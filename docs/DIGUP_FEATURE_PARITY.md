# DigUp desktop-to-web feature parity

Source: pinned DigUp `dc2651ad8299160bbe91e972f857e1a1599a8419`. This is a source comparison, not a deployment certification. The older [audit](architecture/digup-desktop-web-complete-parity-audit.md) describes the engine and platform differences but predates several web changes.

## Reading the matrix

Each numbered row is one verified user-facing capability or closely related workflow, not an individual button. Inputs and outputs are shown as `input → output`. Status describes the **whole row**, not just the presence of a route. Tests named in the final column are acceptance requirements; existing test references do not imply that real-model inference or native integrations passed.

- **Implemented and tested**: connected web behavior has focused tests, with the noted test boundaries.
- **Implemented but not verified**: connected implementation exists, but its claimed runtime path has not been verified.
- **Partially implemented**: some behavior is connected, but material desktop behavior is missing or unverified.
- **Not implemented**: no corresponding connected web behavior was found.
- **Requires native macOS integration**: exact macOS behavior needs a host OS component; other desktop platforms have their own native mechanisms.
- **Blocked by an identified limitation**: a known safety or identity constraint prevents the requested behavior.

Counts are mutually exclusive by status. “Missing” is the sum of Not implemented, Requires native macOS integration, and Blocked; native-required is also reported separately as a subset. “Implemented” in the summary means Implemented and tested only. Platform describes the desktop mechanism and web feasibility, not proof that Linux supports macOS frameworks.

The existing baseline uses the legacy status names above. For newly assessed work, **IMPLEMENTED AND VERIFIED**, **PARTIALLY IMPLEMENTED**, **MISSING IN WEB**, **BLOCKED BY PLATFORM**, **NOT PRESENT IN ORIGINAL DESKTOP**, and **UNVERIFIED** describe the individual capability, with verification limited to the evidence stated. A legacy "Implemented and tested" row is not by itself proof of a complete user-facing workflow.

## Phase 2 search batch

First batch: correct the `strong` boundary returned by [supervisor.py](../backend/app/engine/supervisor.py) when the bridge removes unauthorized, deleted, excluded or otherwise invalid hits. The original boundary refers to the first N original hits; it now counts only retained hits within that prefix, without changing ranking or guessing a new cutoff. The same batch displays the original code line/cell range instead of only its first location. Regression cases in [test_archive_contract.py](../backend/tests/test_archive_contract.py) cover removed strong hits, retained weaker hits and code ranges. This enables a later desktop-style weaker fold without changing the UI layout.

Second batch: `SearchRequest.prefix_last` passes through [archive.py](../backend/app/api/routes/archive.py) and [supervisor.py](../backend/app/engine/supervisor.py) to the unchanged SearchService. [archive-shell.tsx](../frontend/src/components/archive/archive-shell.tsx) first requests keyword prefix hits, then requests the selected keyword/hybrid mode without forced prefix after 120 ms; the second response replaces rather than merges client-side. It folds the returned strong boundary. Filters and limits are passed for both phases; browser requests are aborted on query changes and results are keyed by query and phase. [archive-toolbar.tsx](../frontend/src/components/archive/archive-toolbar.tsx) defers search during IME composition.

The desktop panel also issues `embed_ahead` on each keystroke. The web deliberately does not: SearchService serializes non-render operations and cannot cancel work already received, so speculative embeddings could queue obsolete inference and delay later searches. The final request performs the original embedding after the pause. Browser abort cannot stop a request already being executed by the helper. The existing web-only mode selector is retained; keyword mode finishes with keyword-only results. Tests cover a disposable real keyword index and model-unavailable fallback, plus simulated hybrid responses and browser lifecycle; they do not prove real semantic inference or live browser rendering.

## Strong-match filter counts batch

- Desktop [SearchModel.run](../backend/engine/DigUp/Sources/DigUpApp/SearchWindow.swift#L266) counts kinds in the unfiltered prefix returned by [Searcher.strongCount](../backend/engine/DigUp/Sources/DigUpKit/Searcher.swift#L287). That function takes the leading hits scoring at least half the top score, or all hits when the top score is not positive. [ResultGroupKind.init](../backend/engine/DigUp/Sources/DigUpApp/Results.swift#L159) groups PDF and document hits together; [KindFilters](../backend/engine/DigUp/Sources/DigUpApp/SearchWindow.swift#L501) displays the counts.
- Web [ArchiveShell](../frontend/src/components/archive/archive-shell.tsx) counts only the existing unfiltered response's `strong` prefix, without recalculating scores. The bridge preserves that prefix after removing inaccessible or excluded hits. [ResultFilters](../frontend/src/components/archive/result-filters.tsx) describes the selected limit; no counts are shown from a failed unfiltered response.
- Verification: [search-controls.test.mjs](../frontend/tests/search-controls.test.mjs) covers mixed kinds, weak and boundary cases, filter changes, failures and limits. [test_archive_contract.py](../backend/tests/test_archive_contract.py) covers safe-hit removal and the original engine's filtered limit. Browser display and real-model inference were not verified. Web counts use its selected limit of at most 100, not Desktop's 120, and omit inaccessible hits.

## Matched excerpt highlighting batch

- Desktop [PreviewPane](../backend/engine/DigUp/Sources/DigUpApp/Previews.swift#L123) always calls [WhyItMatched](../backend/engine/DigUp/Sources/DigUpApp/Previews.swift#L320), which displays nonempty excerpts for all non-code kinds, including documents, PDFs, images, screenshots, video and audio. Its pre-existing code excerpt remains in that area; it is not Desktop's full code-lines preview. No full segment text or PDF-page highlighting is retrieved.
- Verification: [preview-pane.test.mjs](../frontend/tests/preview-pane.test.mjs) covers media visibility, expansion, malformed delimiters, multilingual text and HTML-like text escaping with synthetic fixtures. Live browser display and full contextual highlighting were not verified.

## Safety and verification limits

Web sync remains disabled because [Crawler.swift](../backend/engine/DigUp/Sources/DigUpKit/Crawler.swift) may omit inaccessible descendants while [Indexer.swift](../backend/engine/DigUp/Sources/DigUpKit/Indexer.swift) reconciles unseen rows. This safeguard affects deployed code only after deployment; it cannot control a separately running desktop. SearchService startup may create or migrate files, so run engine integration tests only against disposable indexes. Search tests using mocks do not prove model inference, macOS media decoding, desktop watcher behavior or production deployment.
